# Migrating a pip / requirements.txt project

## Detection

Hallmarks:

- One or more `requirements*.txt` files (`requirements.txt`, `requirements-dev.txt`, `requirements-test.txt`, `dev-requirements.txt`)
- README says `pip install -r requirements.txt`
- May or may not have `setup.py` / `setup.cfg` / `pyproject.toml`

## Strategy

The cleanest path:

1. Initialize a uv project (creates `pyproject.toml` if not present).
2. Pin Python.
3. Translate each `requirements*.txt` into the right group.
4. Lock + sync.
5. Preserve the original `requirements.txt` for non-uv users (don't delete it).

## Step-by-step

### 1. Initialize

If no `pyproject.toml`:

```bash
uv init --no-workspace --bare
```

`--bare` skips creating a sample `hello.py`. Use `--lib` if the README treats this as a library (the project is meant to be `pip install`'d), `--app` for an application.

If `pyproject.toml` exists already (e.g. there's a `setup.cfg` that's been modernized partially), don't reinitialize. Read it and keep it.

### 2. Pin Python

```bash
uv python pin <version>
```

Pick the version following the priority rules in SKILL.md Phase 1.

### 3. Translate requirements files

For a single `requirements.txt`:

```bash
uv add -r requirements.txt
```

This reads the file and adds each dependency via `uv add` (so version constraints are preserved and the lockfile is updated atomically).

For a `requirements-dev.txt` / `requirements-test.txt`:

```bash
uv add --dev -r requirements-dev.txt
uv add --group test -r requirements-test.txt
```

### 4. Handle pinned constraints

If `requirements.txt` is fully pinned (every line is `pkg==1.2.3`), it was likely generated by `pip-compile` or `pip freeze`. You have two choices:

- **Preserve pins** — keep the strict equality. Useful when the user wants reproducibility identical to before.
- **Loosen pins** — change `==` to `>=` (or strip pins) and let uv re-resolve to current versions.

Default to **preserving pins** when migrating an active project (don't surprise the user with version bumps). Loosen only if the user explicitly asks for a refresh.

If pins are too tight to resolve (e.g. transitive conflicts surface that pip silently ignored), report the conflict and ask the user which pin to relax.

### 5. Handle special requirements.txt syntax

Watch for:

- `-e .` or `-e ./subpkg` — editable install of the local package. uv handles this automatically when `pyproject.toml` is present and the project is a package; remove the `-e .` line.
- `-e git+https://...` — `uv add --editable git+https://...`
- `-r other.txt` — recursive include. Process the included file too.
- `-c constraints.txt` — constraint file. uv supports `--constraint` on `uv add` if needed; usually safe to skip and let uv resolve fresh.
- `--index-url` / `--extra-index-url` — set in `pyproject.toml` under `[[tool.uv.index]]`. See `references/warnings.md` for private indexes.
- `--find-links` — local wheels. Map to `[tool.uv.sources]` or document as a warning.
- Comments starting with `#` — drop, but capture any pinning rationale into UV_SETUP.md.

### 6. Local package install

If the README says `pip install -e .` after `pip install -r requirements.txt`:

- The project is also a package. `uv sync` installs it automatically when `pyproject.toml` has `[project]` with a `name` and `version`.
- Make sure `[project]` exists in `pyproject.toml` and has the source dir configured (`[tool.hatch.build.targets.wheel]` or similar — `uv init --lib` sets this up).

### 7. Validate

```bash
uv sync
uv tree
```

If sync fails, the most common causes are:

- Conflicting transitive versions → relax a pin or pick a more recent base version.
- Missing wheel for current Python version → bump Python or relax `requires-python`.
- Package not on PyPI → see warnings.md.

## What to preserve, what to delete

**Preserve** (don't delete):
- `requirements.txt` and friends — they're a fallback for non-uv contributors and CI.
- `setup.py` if it has custom build logic — but most can be replaced by `pyproject.toml`.

**Replace**:
- `setup.cfg` metadata → migrate to `[project]` in `pyproject.toml`. Delete `setup.cfg` only if it had nothing but metadata.

**Add**:
- `pyproject.toml`, `uv.lock`, `.python-version`

## Common gotchas

- **`pip install` flags inside requirements.txt files**: `--no-binary`, `--only-binary` aren't directly portable — document as a warning.
- **Platform-specific deps via `; sys_platform == 'linux'`**: uv supports environment markers in `[project.dependencies]`; preserve them.
- **`numpy`/`scipy`/etc. with specific BLAS**: the wheel works fine; the BLAS impl (OpenBLAS, MKL) comes with the wheel. If the project specifically wants MKL, that's a conda-style requirement — see warnings.md.
